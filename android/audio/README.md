# Experimental Ruby Audio bridge

This component has been tested independently; its full game integration remains experimental. `lunetile_audio_register` binds a Java `AudioBridge` to Ruby `Audio`. It exposes XP `bgm_play`, `bgs_play`, `me_play`, `se_play`, their four `stop` methods, and `bgm_fade`, `bgs_fade`, `me_fade`. Volume is clamped to 0–100 and pitch to 50–150 like the inspected Lunetile XP implementation. File paths are relative to an explicit resource root, may omit `.ogg`, `.wav`, `.mid` or `.midi`, and may not escape that root. MIDI accepts SMF type 0/1 headers; other extensions are rejected.

Calls wait for the Java playback worker to process the request. Immediate Java errors become Ruby `RuntimeError`; a later asynchronous player error is reported on the next Audio operation. A 15-second worker timeout is reported as an error and does not prove that an already queued operation was cancelled. Ruby calls must be made on a Java-attached thread. The host must stop using Ruby methods before unregistering the JNI global reference and close the Java bridge as part of its lifecycle.

The isolated ARM64 Ruby/JNI diagnostic was run on an Android 36.1 x86_64 emulator with ARM64 translation. It checked play/stop, default and clamped arguments, WAV/OGG and synthetic type 0 MIDI, relative paths and missing, unsupported, escaped, corrupt and nil argument errors. It also checked that all three faded channels were stopped after the requested duration and that the bridge could close. These checks do not establish actual pitch accuracy, output quality, seamless loops, physical-device behavior, or full game integration. See `android/host/README.md` for MediaPlayer tests and their limits.
